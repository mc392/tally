When Matt shares a real export to show a format, use it only to learn the layout and to run counts-only checks; never copy a row, merchant, name, sort code or amount from it into the repo.

Real figures were once in `tests/engine.test.js` and were removed by rewriting history - don't reintroduce anything shaped like them.
- **Figures are hidden every time the app opens, and every time you come back to it** (`meta.private = true` at start-up; `hideFigures()` on `visibilitychange`→hidden, `pagehide`, and a bfcache `pageshow`): the eye in the header shows them until you next leave. - No build step, no framework: plain HTML/CSS/JS served by GitHub Pages. Keep it that way unless there's a strong reason.
- iOS-native look: system font, inset grouped lists, large titles, bottom tab bar, bottom sheets. Main screen stays simple; detail lives one tap deeper.
- `engine.js` is pure maths with no DOM access. Any change to projection logic must keep `node tests/engine.test.js` passing, or update the test with a written reason.
- **Tally talks to no server but its own.** The Content-Security-Policy in `index.html` makes the browser enforce it. No inline scripts or `onclick=` attributes (the policy blocks them); no third-party scripts, fonts or APIs.

## Storage (`storage.js`, Phase 1 - Sep 2026)
All reading and writing of the finance file goes through `storage.js`; `app.js` asks it for a route and never touches a file API directly.
- **Routes.** `live` = Chrome/Edge on a computer holding a file handle with permission: every `changed()` autosaves 1.2s later. `reconnect` = the handle survived a reload (it is kept in IndexedDB) but the browser wants one tap to grant write access again. `manual` = everything else (iPhone share sheet, download). Phase 2 adds a `native` route here for the iOS shell.
- **Writer mark.** Every save stamps `writer {device, label, rev, at}` on the file; `meta.base` is the mark this device last read or wrote. Before a live write the file is read back, and `isConflict(fileWriter, base)` refuses to write over a mark it has not seen - the header shows *File changed* and the sheet offers load-theirs or overwrite. A file with no mark (older files) is never a conflict. Manual routes cannot read back, so they cannot check. `syncFromFile()` loads a newer file on start and when the app returns to the front, but only if nothing here is unsaved.
- **Encryption.** Optional. AES-GCM-256, key from PBKDF2-SHA256 at 600,000 rounds, fresh 12-byte IV on every save, salt in the file. The envelope is `{app, format:"tally-encrypted", v, kdf, iv, ct, writer}` - the writer mark is outside the sealed part so a conflict is spotted without decrypting. The key is a **non-extractable** `CryptoKey` kept in IndexedDB (`seal`), so the passphrase is asked once per device. There is no recovery: a forgotten passphrase means an unreadable file, and the UI says so.
- **The working copy on the device (localStorage `tally.v1`) is not encrypted.** Encryption protects the copy that leaves the device. Phase 3 may lock the working copy behind Face ID.
- `edits` counts changes so one made while a save is in flight is not marked saved.

## Data file shape (version 12, Sep 2026)
`model.js` owns the shape: `TallyModel.migrate()` upgrades any older file on open (`normalise()` calls it first), and the file on disk only changes when it is next saved. `engine.js` only ever sees the current version. **A change to the shape means bumping `VERSION`, adding a step to `migrate()`, and a test in `tests/migration.test.js`.**
`people[]`, `accounts[] {id,name,owner,type,rate,rates?[{from,rate}],active,note,access?,noticeDays?,maturity?,flexible?}`, `snapshots[] {date, balances{accountId: amount}, contrib?{accountId: £ paid in since the update before}}` (liabilities negative; contrib: v8; **any subset of accounts** since v9), `reviews {'acc|from|to': {status,at,note}}` (v9), `rules.checks {abs, pct}` (v9), `goals[] {id,name,target,date,accounts[]}` (v8),
`flows[] {id,name,kind:'income'|'spend'|'oneoff',amount,start,end,category,owner,inflates,growth,bundle,on,linked?,settles?,overrides?{'YYYY-MM':£}}` (overrides: v6), `bufferPct`,
`bundles[] {id,name,template,start,on,scale,contingency}` (v3, life events),
`remortgageOptions[] {id,partId,name,type,rate,fixMonths,fee,feeAdded,lump,regular,capPct,termMonths,afterRate}` (v5),
`transactions[] {id,account,date,amount,description,merchant,bankCategory,category?,source,batch,type?,detail?}`, `imports[] {id,at,account,format,count,dupes,from,to}`, `categoryRules[] {id,contains,category,min?,max?,account?}`, `categoryMap {bankCategory: category}` (v7),
`mortgage {propertyValue, parts[] {id,name,payment,balance,rate,fixEnd,newRate,termEnd,rateModel?}}`, `accounts[].rateModel?`, `rateBasis {source,asOf,curve,previous?}` (v11, market rates),
`rules {cashFloor,isaPerPerson,isaUsedBy{personId:£},isaFillOrder[],isaUsedTaxYear,sweepToSS,remortgage{leadMonths,decideMonths,earmarkMonths,warnAt,glide,glideMonths,target}}` (remortgage: v4), `scenarios{key:{name,growth,ssReturn,inflation,payRise,option,bundles{},rateShift,rates{kind,…},lines{flowId:{on?,amount?,start?,end?}},mortgage{partId:{path,rate?,years?,option?}}}}` (plan fields: v5; rates: v11; lines, mortgage: v12), `scenario`, `horizonMonths`.
- **Flows** replaced v1's `income[]`, `spending[]` and `events[]`. Income and spend amounts are **monthly and positive**; a one-off is the total, **signed** (− = money out) and happens in its `start` month. `start`/`end` are `'YYYY-MM'` or null; `TallyModel.flowActive(f, k)` is the only test of whether a flow counts in a month. `monthlyBudget(data, 'YYYY-MM')` is the regular budget for one month (one-offs excluded). `linked:'mortgage'` on a spend flow is how the mortgage enters spending. `bundle` names the life event a flow belongs to.
- **A newer file is refused.** `loadText()` will not open a file whose `version` is above `TallyModel.VERSION`: an out-of-date copy of the app (the service worker serves the cached one first) would drop what it does not know about and save the loss back.
- **ISA allowance is per person** (`isaPerPerson`, default £20,000), filled in `isaFillOrder` - the first person's allowance is used up before the next person's (decided with Matt). The Joint person (`id:'J'`) never holds an ISA. Migration splits the old household figure evenly and puts what was already used against people in fill order, which keeps every projected figure identical. Re-deposit room is still tracked for the household, and every cash ISA is treated as flexible in the projection; `accounts[].flexible` is recorded for Phase 1 readiness but not yet used by the engine.
- **Access** (`instant|notice|fixed|invested|locked`, labels in `TallyModel.ACCESS`): defaulted by type on migration; liabilities have none. Recorded now, used by the Phase 1 readiness ladder.
- **Pension** is an account type (pool `other`, grows at its own rate like savings, access `locked`).
Account types: ss_isa, cash_isa, savings, current, pension, card, card_0, tax. Cash pool = current + card. ISA pot = ss_isa + cash_isa.

## Remortgage readiness (Phase 1.1-1.3, Sep 2026)
- **`readiness(data, scenario, 'YYYY-MM')` in `engine.js` is the one answer** to "what will be free at the remortgage". It works towards the **earliest** mortgage part's fix end still to come (decided with Matt); later parts are listed and get their turn when that one passes. "At the fix end" = balances at the end of the month **before** the switch month.
- **Available to overpay = instant + within weeks − cash floor − earmarks.** Earmarks are the positive `rows[].earmark` of the `earmarkMonths` (12) months from the switch: one-off payments out, plus life-event costs and life-event pay drops. S&S ISAs are shown (every scenario, and markets −20%) but never counted as available.
- **`rows[].byAccess` {instant, notice, invested, fixed, locked, debts} adds up to `net` every month** - there is a test. A fixed account counts as instant from its maturity month. Liabilities (cards, tax) are `debts`.
- **Cash ISAs marked fixed or notice are held apart** (`heldIsa`): never drawn on to top up the floor, grow at their own rate, and a fixed one joins the ordinary cash ISA pool when it matures. Every migrated cash ISA is instant, so existing figures do not move. `isaCash` in a row still includes them; `isaCashFlex` is the drawable pool.
- **Glide path and target (1.3)** act only on the S&S share of top-ups before the fix end: glide sends none to S&S in the last `glideMonths`; a target lets S&S take only what is left once available would still reach the target. Neither moves money that is already invested.
- **Warnings (1.2):** `checkLeak()` runs in every `changed()`, compares available with the figure before the change, and raises `ui.leak` (the orange chip) when it drops by more than `warnAt` (£5,000). It uses the default scenario, not the one being viewed.

## Remortgage deals and whole-plan scenarios (Phase 1.4, 1.6, Sep 2026)
- **`amortise(option, balance, months)` is the pure maths** of one deal: annuity payment on (balance − lump + fee if added), rate for the fix then `afterRate`, regular overpayments capped at `capPct` % of the balance at the start of each deal year. `project()` applies **the same rules** to a part from its fix end when the scenario's `option` names a deal for that part - there is a test that the two agree month by month. Lump sum, an upfront fee and overpayments leave cash as `rows[].dealCash` (they are not spending, so no buffer on them).
- **An option with no `termMonths` runs over what is left of the part's term** (`termEnd − fix end`) in both the household projection and `rateGrid()`. Keep those consistent.
- `compareOptions()` runs "Do nothing" (the part's own rate after the fix) and each deal for the earliest-fixing part through `projectAs()` - the household projection with scenario settings changed, never touching `data` - so every figure on Compare deals is what that scenario would show on its own.
- **A scenario is a whole plan (1.6, paths v12):** assumptions + `bundles` (per-scenario on/off, absent = the event's own switch; `TallyModel.bundleOn`) + `lines` + `mortgage` + `rateShift` (added to tracker rates and rates after a new fix only - never to an existing part's own reversion rate, so existing figures do not move). Plans can be added, copied and deleted (`planAddSheet`, `planDelete`); **never assume a key exists** - `defaultSk()` / `scenarioKey()` fall back to the first plan.
  - **`sc.lines[flowId]`** is this plan's version of a line: `on`, `amount`, `start`, `end`, applied **last** in `effectiveFlows(data, sc)` (so a plan's amount is the amount, not scaled again by a life event). A line "only in this plan" is a flow saved `on:false` (+ `plan:` the key it was made in) that the plan switches on; `flowWhen()` says which plans have it, and deleting the last plan that uses it deletes it.
  - **`sc.mortgage[partId]`**: `as` | `float` | `fix` (`rate`, `years`; no rate on a market-rate part = a refix priced from the curve) | `deal` (`option`). In `project()` each part gets its own `optAt` (a saved option, or a `fix` as an option with no fee returning to the part's `newRate`); `float`/market `fix` change the part's rollover when its path is built. The older `sc.option` moved here on upgrade and still works - it is how `projectAs(..., {option})` tries a deal - but only for a part the plan says nothing about; **Compare deals sets that part to `as`** so it measures exactly the deal.
- **Compare plans is a gallery** (`CMP_CHARTS`, chosen per device in `localStorage['tally-cmp-charts']`, default `CMP_DEFAULT`): 12 over-time lines, 3 "on a date" views (where the money is, why they differ, scorecard) and 2 timelines (tight months, what happens when). **Every figure comes from `TallyAnalysis.comparePlans(data, keys, months, at)`**, tested in node; the screen only draws. "Tight months" measures reachable money (cash + instant cash ISAs) above the floor, because the projection holds cash itself at the floor. Up to three plans, 3/5/10 years; the key-dates table stays.

## Balances per account (Sep 2026)
**Each account has its own dated balances.** A snapshot may hold one account or all of them; nothing assumes an update covers everything.
- **`balanceOn(data, id, date)` in `engine.js` is the one answer** to "what did this account hold then", with `how`: `observed`; `interest` (savings and cash ISAs: the last balance grown at the account's rate, compounded daily over 365, plus money in and out grown from its own date; interest recorded by hand is not added on top); `transactions` (current accounts and cards that have any: last balance plus transactions since, or before the first balance, the next balance less those in between); `straight` (anything else between two balances); `carried` (after the last one). A closed account is not carried past its last balance.
- **`positionOn(data, date)`** is every account on a date in the snapshot shape, and **`latestSnapshot(data)` now returns `positionOn(latestDate)`** - so the projection, readiness, goals and everything else start from all accounts even after a one-account update. With a full update on the latest date it is exactly that update, so existing files project unchanged (every earlier test passes untouched).
- **Anything that shows a balance on a date goes through `positionOn`**, never `snapshot.balances` directly: Overview, pools, Accounts, history, attribution and drift all do. History charts are month-ends between the first and latest balance, each a worked-out position.
- **The update sheet leaves savings and cash ISAs blank** (placeholder: the estimate) on a new update, so they keep rolling at their rate; blank is not stored. Each account's page has *Add a balance for this account* (upserts into that date's snapshot, or a new one-account snapshot) and *Record money in or out* - a manual transaction `{source:'manual', kind:'in'|'out'|'interest', category:'Transfer'|'Income'}` that the inference, the checks and attribution all read.
- **The full update has a tick per account.** Untick one and nothing is recorded for it on that date (it keeps being worked out from its own balances), so a stale figure is never stamped as a new balance. Correcting an update, an account not in it starts unticked; saving onto a date that already has an update keeps what a left-out account already had there. The total counts a left-out account at its worked-out value.
- **History charts count an account only from its first balance** (`positionOn(data, date, {entered:true})`: Overview, pools, Balance history), so nothing worked backwards from a later balance is drawn, and **start at the first update you entered yourself** (`firstSubmitted()`): a date only a statement import recorded is marked `snapshots[].source:'import'` and does not start them, because before your own first update net worth would be one account on its own. An account's own chart still starts at its own first balance.
- **Lloyds statements record their own balances** on import (optional, on by default): the newest row's running balance, and the oldest row's balance less its amount dated the day before (so that day's rows count after it). The checks for that span then reconcile exactly.
- **`checks(data)` in `analysis.js`**: for every account, every gap between two of its balances - current/card (with any transactions): change vs transactions; savings: the second balance vs the first grown at the rate plus money recorded; S&S ISAs and pensions: the implied money-weighted return to cross-check. Material above `max(rules.checks.abs, pct % of the balance)` (£100 / 1%). A review is stored under `'account|from|to'`, so a new balance in the gap asks again. Accounts never imported are not checked by transaction.
- **Interest rates are dated (v10): `accounts[].rates [{from:'YYYY-MM-DD'|null, rate}]`.** `from:null` is the rate before any change; each entry applies from its date until the next. `TallyModel.rateOn(a, date)` and `growthFactor(a, d1, d2)` (piecewise daily compounding over 365, split at each change) are the only way a rate is read - `balanceOn`, `checks`, attribution and the projection (each month's rate; the cash ISA pool weighted by opening balances) all use them. Because a figure for a date only ever reads rates in force up to that date, **adding, correcting or removing a change never moves a balance before it**. `a.rate` is kept as the rate in force today (display only, and for older copies); it is edited only when an account is created - after that, through *Interest rate* on the account's page (`ratesGroup`/`rateSheet`).
- **Account labels.** Pickers use `accOption` - "Name · Owner · Type" - in a full-width stacked field (`.field.stack`: the default `.field select` is right-aligned and 52% wide with `direction:rtl`, which cut long names from the left). Everywhere else a name goes through `accLabel`/`accName`, which add "(Owner)" only when another account has the same name.
- Attribution now compares positions, takes recorded money in and out as contributions (dividends kept in are growth), and for savings uses the change less recorded flows as interest when any are recorded, the rate estimate when none are.

## Analysis and risk (Phases 3-4, Sep 2026)
`analysis.js` (`TallyAnalysis`) is pure, built on `engine.js`, and tested in node.
- **Where the change came from (3.1)** - `attribution(data, date1, date2)` puts every account's change in one of four piles that **add up to the change in net worth exactly**: growth (S&S ISAs and pensions, less `snapshots[].contrib` paid in, which the update sheet now asks for), interest (savings and cash ISAs: average balance × the growth at the account's dated rates over the period, `growthFactor − 1`, an estimate), debt (0% cards and tax owed going down), and money put in (the rest; paying a debt from cash shows here as negative and under debt as positive, netting to nothing). Per investment account a Modified Dietz money-weighted return, annualised. Shown on each balance update's page.
- **Goals (3.2)** - `goalStatus()`: accounts the projection tracks on their own (`rows[].accounts`, added for this) are read directly; pooled ones (cash, instant cash ISAs, S&S) take their share of the pool by today's balances. On track, when reached, extra a month needed (simple, no growth). Goal dates are dashed green lines on the projection chart.
- **ISA tax year (3.3)** - `isaYear()`: per person, allowance, paid in (as entered in Rules), planned by 5 April (from the projection's `freshBy`), left unused; re-deposit room separately. `nudge` in February and March shows a chip on Overview.
- **Today's money (3.4)** - `realValue()` deflates by the scenario's inflation compounded monthly from the projection start. A display toggle on Projection; nothing stored.
- **Range of outcomes (4.1)** - `monteCarlo()`: 2,000 paths, monthly S&S returns drawn normally around the scenario's return (0 when growth is off) with `vol` % a year, passed to `project()` as `opts.ssReturns` (used instead of the scenario's S&S return). **Seeded** (mulberry32 + Box-Muller), so it is testable and repeatable; with no volatility every path equals the ordinary projection - there is a test. It runs in `mc-worker.js` (a Web Worker; falls back to 500 paths on the main thread if workers are unavailable). Cash and savings rates are not varied.
- **Stress tests (4.2)** - `STRESSES` / `stressed()`: markets −25% next month (`opts.ssShock`, and the update's S&S balance scaled for readiness), no bonus (one-off money in and income named "bonus" removed), rates +2% at the remortgage (every part's rate after its fix and the scenario's `rateShift`), the biggest income stops for 6 months (month overrides of 0), a £10k cost next month. Each reports floor breaches, lowest cash and the change in available to overpay.
- **Balance reminders (5.5)** - a calendar file (`reminderICS()`, RFC 5545, CRLF line ends) with a monthly event on the 1st and a 9am alert. No server.

## Bank statements (Phase 2, Sep 2026)
`transactions.js` (`TallyTx`) is pure and tested in node. Amounts are from the **account's** point of view: − = money out.
- **Formats** are recognised by their header row (`FORMATS`): **Lloyds** (debit/credit columns, a leading `'` on the sort code, amounts like `.25`, rows with a blank type) and **American Express** (a charge is positive in the file and a payment negative - reversed on import; addresses run over several lines inside quotes; a `Category` column). Anything else goes through a column-mapping sheet (`genericRow`). Monzo and Trading 212 are not added yet: only formats seen in a real export are trusted.
- **Ids are derived, so importing the same file twice adds nothing** (`fresh()`): Lloyds uses the running balance, Amex its reference, anything else the whole row plus its position among identical rows - two identical coffees on one day are two transactions. Each import is a `batch`, and Plan › Imports removes one as a whole.
- **`categorised(data)` is the one place categories are worked out**, every time, so a new rule applies to everything already imported: set by hand (`t.category`) > `categoryRules` (first match) > the bank's own category through `categoryMap` or a guess > a short list of common UK merchants > money in = Income > Uncategorised. Setting one transaction with "all from this place" writes a rule on its `merchant`.
- **`merchantOf()` works from the RAW description.** Amex pads the town onto the end after a run of spaces, and sometimes one space, so the Amex reader also strips its own Town/City value. `clean()` collapses spaces, so running it first loses that.
- **Transfers:** `transferPairs()` matches equal and opposite amounts in two different accounts within 5 days (paying the card from the current account) and marks both `Transfer`, unless a rule or a hand setting says otherwise. Transfers, Income and Ignore never count as spending.
- **`budgetVsActual(data, 'YYYY-MM', ctx)`**: plan = spend lines running that month (the mortgage line at its payment) + one-offs planned for it; actual = money out less refunds per category. Only imported accounts are counted and the screen says so. `recalibrate()` averages the last three complete months and lists categories more than 10% (and £20) off plan; the screen offers to set a single plan line to the average.
- **`recurring()`**: same account and merchant, a steady gap (weekly to yearly), similar amounts, three payments (two for yearly). Flags new, a price rise since the last change within the last few payments, and stopped.
- **Spending insights** (`vInsights`, Plan › Spending insights): `TallyTx.insights(categorised, {months, prevMonths, measure, by, account, focus, partial})` is the only arithmetic - spending (money out less refunds, not the special categories), money in (Income) or both, by month and by category / shop / account, against the window before, `movers` (last 3 whole months against the 3 before, at least £20 a month and a tenth) and the largest items. **The month still running is drawn faded and never totalled, averaged or compared**; `insWindow()` builds windows of whole months ending at the newest whole month with transactions, and only offers the window before when every month in it has data. The headline says how many months it really covers when there are fewer than the period asks for. A row opens that group split the other way (`INS_NEXT`); `txns:ins=<json>` lists exactly the transactions behind any figure. Tests: `tests/insights.test.js`.

## Cash-flow calendar and plan vs actual (Phase 1.7, Sep 2026)
- **A month set by hand** is `flow.overrides['YYYY-MM']`, read through `amountAt(f, k, factor)` in `engine.js`: the figure is that month's actual amount, so **no inflation or pay rise is applied on top**. Every place that reads a flow's amount must go through `amountAt` (the projection, `monthlyBudget`, earmarks, life-event net). A life event's `scale` applies to its overrides too. Putting a month back to the usual amount removes the override.
- The calendar is 24 months from this month; a month opens a sheet with every running income and cost (not the linked mortgage line - that comes from the mortgage) and its one-offs, and can add a one-off in that month.
- **`drift(data, sk, date)`** compares a balance update with what the projection from the *previous* update expected at the end of the month before it: cash, ISAs, and savings/pensions/debts. Without transactions it cannot split cash between "spending over" and "income under", and cannot split ISAs between markets and contributions, so the screen names both possibilities rather than guessing. Recalibration from actual spending (the rest of 1.7) waits for Phase 2's transactions.

## Market rates from yield curves (Sep 2026)
`docs/YIELD_CURVES.md` is the plan, with a status box saying how it landed. `curves.js` (`TallyCurves`) is pure and tested in node.
- **Opt-in per item.** A savings account, cash ISA or mortgage part with a `rateModel` follows the scenario's rate path; **one without keeps its own entered rates exactly as before**. `project()` builds each path once (`TallyCurves.path`) and reads `rates[i]` month by month; `rows[].rates`, `.interest`, `.market` (workings), `.cashIsaRate`, `mortgageParts[].rate/.repriced/.why` feed the month detail.
- **`TallyCurves.forScenario(data, sc)`** is the one place a scenario's rates are resolved: `{active:false}` for `flat` and whenever no curve is to hand - and then the engine is the old engine to the penny (a test compares every row over 120 months). Keep it that way: anything new the layer does must be skipped when it is inactive.
- **Calibration**: a variable item's spread is set so the first modelled month is its entered rate, against the scenario's *starting* curve (so a shift is not absorbed). A dated change still to come is a fact; the model starts from the last one.
- **Fixed**: the entered rate until `maturity` (accounts) / `fixEnd` (parts), then `rollover`: `variable` (default; calibrated to `newRate` for a mortgage, the quoted instant rate or today's rate for savings), `refix` (AER of the forward for the new term + margin; money stays locked, so readiness sees it), `manual`, `close` (savings → cash; a cash ISA → the instant pool). A scenario's chosen remortgage deal overrides the part's path from the switch. `sc.rateShift` is added to modelled trackers and new fixes only.
- **The curve lives in the finance file** (`rateBasis`), fetched from `rates/curve-latest.json` on the app's own site and adopted only when the user taps. The pipeline (`scripts/fetch-curves.mjs`, `.github/workflows/rates.yml`) is the only thing that writes `rates/`; never commit a curve by hand, and never a made-up one there - test curves live in the tests.
- IADB series codes live in `scripts/rates-series.json`; only fill in a code checked against the Bank's database.

## Life events (Phase 1.5, Sep 2026)
A life event is a **bundle**: a row in `bundles[]` plus ordinary flows carrying `bundle: id`, with real dates.
- **`TallyModel.effectiveFlows(data)` is the one place bundles are applied** - an event that is off drops all its lines, `scale` multiplies every line, `contingency` % is added to its costs (spend, and one-offs that are money out). `project()` and `monthlyBudget()` both read through it; anything new that totals flows must too.
- **A drop in pay is a NEGATIVE income line** in the event (e.g. parental leave: pay during leave − usual pay). That is what makes switching the event off restore usual pay exactly, without touching the ordinary pay line. `payDip()` in `templates.js` writes it from the person's usual pay in the start month.
- **Shifting** an event (`shiftBundle`) moves its start and every line's start/end by the same months; changing *Starts* on the event's page does this.
- `templates.js` (`TallyTemplates`) is pure: each template has `fields(ctx)` in the form-sheet shape, `defaults(ctx)` and `build(params, ctx)` returning lines with **offsets** from the start month; `applyTemplate()` turns them into dated flows. Every amount is a placeholder, and anything that depends on a government rate (Child Benefit and the High Income Child Benefit Charge, childcare funded hours, statutory pay, stamp duty) carries a note to check gov.uk rather than a figure presented as fact. Stamp duty is entered by the user, not calculated - bands change and differ by nation.
- The property template does **not** change the mortgage parts; it records the payment change as a cost and says so.
- Life-event lines are kept off the ordinary Plan lists and one-offs page; they live on the event's own page (`bundle:id`). Each month's `rows[].bundleNet[id]` is the event's net effect that month, which reconciles exactly to its effect on net worth (with no buffer); the month detail lists it and the projection charts shade each event's span.
- Adding from a template is three sheets: pick → answer its questions → **review every line** (each can be changed or left out). Nothing is written until the last Save.

## Mortgage parts (Sep 2026)
A mortgage is a list of **parts** (UK sub-accounts: e.g. the original loan plus a further advance), each with its own payment, balance, rate, fix and term; `propertyValue` stays on the mortgage because there is one home.
- **Older files hold one flat mortgage.** `normalise()` turns it into a single part (`id:"main"`) and moves `propertyValue` up; `engine.js`'s `mortgageParts()` reads the flat shape too, so the engine works on either. Always go through `mortgageParts()` / `mortgageTotals()`, never `data.mortgage.payment`.
- Each part runs on its own in `project()`: interest at its rate, a payment recalculated by annuity when *its* fix ends. `rows[].mortgageParts` has the per-part figures; the old `mortgagePay/Interest/Bal` are the totals.
- **One behaviour change:** a part whose balance reaches zero now stops costing anything, so its payment leaves the spending. Before, a paid-off mortgage kept charging its payment for ever. For every mortgage not paid off within the horizon the figures are identical to the previous engine (checked on 20,880 figures across six single-mortgage cases over 120 months).
- The mortgage is only counted in spending through a spending line with `linked:"mortgage"`, as before.
- With one part the screen shows its details as it always did; the list appears from the second part on, and the original is named "Part 1" at that point.
- `node tests/mortgage.test.js` - expectations worked out by hand from the rule.

## Switches
`.switch span` has `pointer-events:none` so a tap reaches the checkbox beneath it. Before Sep 2026 it did not, and tapping any switch in the app did nothing. Tests click the `input`, never the span.

## Projection rules (from the original spreadsheet)
Monthly: cash + surplus + one-off items. Above the cash floor → sweep into ISAs up to (new allowance + flexible re-deposit room). Below → withdraw from ISAs (cash ISAs first); withdrawals add re-deposit room for the rest of that tax year. Allowance resets each April. Growth optional per scenario.
